# ReleaseGuard AI

**Evidence-backed release risk analysis for pull requests.**

ReleaseGuard AI is a local-first release governance prototype. It accepts a release change set, runs deterministic checks, produces traceable findings, calculates a transparent risk score, and generates a human-reviewed release decision.

> **Status:** MVP in active development. The local workflow is the supported path today. Azure, hosted LLM agents, and live GitHub webhook integrations are planned extensions, not claimed as deployed capabilities.

## What it does

- Inspects changed files for selected high-risk patterns (secrets, unsafe configuration, risky code constructs).
- Checks Python and .NET dependency manifests against a local advisory snapshot (no network calls in the default run).
- Accepts test results and coverage metadata to highlight verification gaps.
- Produces structured findings with file/line evidence where available.
- Calculates a deterministic 0–100 risk score using documented weights.
- Creates a deployment checklist and rollback plan.
- Requires a human to approve or reject a release; it never deploys to production.

## Quick start

Requirements: Python 3.11+

```bash
python -m venv .venv
# Windows: .venv\Scripts\activate
# macOS/Linux: source .venv/bin/activate
pip install -e ".[dev]"
uvicorn releaseguard.main:app --reload
```

Open http://127.0.0.1:8000/docs for the API.

Submit a local assessment:

```bash
curl -X POST http://127.0.0.1:8000/api/releases \
  -H "Content-Type: application/json" \
  -d @data/sample-release.json
```

The response includes a release ID. Fetch its report at `GET /api/releases/{id}/report`.

Run tests:

```bash
pytest
```

## API

| Method | Endpoint | Purpose |
|---|---|---|
| POST | `/api/releases` | Create and analyse a release submission |
| GET | `/api/releases/{id}` | Retrieve assessment summary |
| GET | `/api/releases/{id}/findings` | List evidence-backed findings |
| GET | `/api/releases/{id}/report` | Retrieve decision, score and release plan |
| POST | `/api/releases/{id}/approve` | Record human approval |
| POST | `/api/releases/{id}/reject` | Record human rejection |
| GET | `/health` | Liveness check |

## Risk model

The initial configurable model is:

`R = 0.30S + 0.25C + 0.20D + 0.15T + 0.10A`

Each dimension is normalised to 0–100: security (S), code quality (C), dependency risk (D), testing confidence (T), and API compatibility (A). Higher values mean higher risk. The weighted result is rounded to an integer.

The score is computed by code, not generated by an LLM. Thresholds and weights are documented in [docs/risk-scoring.md](docs/risk-scoring.md). They are initial policy defaults, not empirically calibrated claims.

## Safety boundaries

- No arbitrary execution of pull-request code.
- No production deployment or automatic merge.
- Findings should include evidence; heuristic matches are labelled as such.
- Do not submit real credentials or customer data to sample payloads.
- A future GitHub integration must be read-only by default and verify webhook signatures.
- Treat PR descriptions and source comments as untrusted input, including prompt-injection attempts.
